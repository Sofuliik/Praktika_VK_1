## 2. Поднятые сервисы — и почему именно они


| Сервис | Роль в стеке                                                                                                        | Почему именно он (а не альтернатива)                                                                                                                                                                       |
|--------------|-------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| MinIO        | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Открытый исходный код, полностью совместим с AWS S3 API, позволяет запустить локально в Docker без затрат на облако.                                  |
| PostgreSQL   | БД, где Lakekeeper хранит метаданные каталога                                                    | Надежная реляционная СУБД, которая используется Lakekeeper для хранения состояния каталога и обеспечения ACID-свойств при коммитах. |
| Lakekeeper   | Iceberg REST Catalog - каталог метаданных таблиц                                                       | Написан на Rust, легковесный, поддерживает REST API (в отличие от тяжелого Hive Metastore), использует PostgreSQL для надежности.                              |
| Trino        | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO       | Работает по модели MPP, отлично подходит для OLAP-запросов и умеет работать с Iceberg через REST-каталог. Есть встроенный генератор TPC-H.  |
| DBeaver      | SQL-клиент                                                                                                              | Удобный интерфейс для выполнения запросов и просмотра структуры каталогов `bronze`, `silver`, `gold`.                                                                  |


### Скрипты, которыми поднимала стек

```powershell
# MinIO используется для хранения файлов данных Apache Iceberg в формате Parquet:   
docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin -v minio-data:/data quay.io/minio/minio:latest server /data --console-address ":9001"  
  
# PostgreSQL используется для хранения служебной информации Lakekeeper:  
docker run -d --name lakehouse-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 -v pg-data:/var/lib/postgresql/data postgres:17  
  
# Использованная команда запуска Spark (из конфигурации работы):  
docker run --rm -e "LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!" -e "LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres" -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres" quay.io/lakekeeper/catalog:latest-main migrate  
  
# Lakekeeper используется в качестве REST-каталога Apache Iceberg:  
docker run -d --name lakekeeper -e "LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!" -e "LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres" -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres" -p 8181:8181 quay.io/lakekeeper/catalog:latest-main serve  
  
# Trino используется в качестве основного SQL-движка.  
docker run -d --name trino -p 8080:8080 -v "${PWD}\catalog:/etc/trino/catalog" trinodb/trino:476
```


Для проверки состояния сервисов использовалась команда: docker ps


По результатам проверки все четыре основных контейнера находились в состоянии `running`.



## 3. Разбор запроса — какие данные нужны


| Таблица TPC-H | Нужные колонки                      | Что запрос с ними делает (фильтр / джойн / агрегат / вывод)                                                                                                |
|----------------------|--------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `lineitem`           | `orderkey`, `quantity`                           | Агрегация `sum(quantity)` для поиска заказов, где суммарное количество товара > 300. Также используется для джойна. |
| `orders`             | `orderkey`, `custkey`, `orderdate`, `totalprice` | Джойн с `customer` и `lineitem`. Сортировка по `totalprice` и вывод даты.                                                                                                |
| `customer`           | `custkey`, `name`                                | Джойн с `orders` для получения имени клиента. Вывод в витрину.                                                                                             |

## 5. Тесты производительности


| Сжатие на Bronze | Время запроса | Размер, МБ | Твой вывод (что лучше и почему)                                                                     |
|--------------------------|---------------------------|--------------------|-----------------------------------------------------------------------------------------------------------------------------|
| GZIP (`orders_gzip`)     | 10 сек                 | 35,9               | GZIP медленнее при чтении из-за высокой нагрузки на CPU при распаковке. |
| ZSTD (`orders_zstd`)     | 5,1 сек                | 35,9               | ZSTD быстрее читается. Оптимальный выбор для Silver-слоя.                             |


(Примечание: Trino проигнорировал настройку `compression_level` при создании `orders_gzip`, поэтому размеры файлов совпали. Однако разница во времени чтения подтверждает теоретические данные из лекции 7: ZSTD быстрее GZIP.)

## 6. Часть 2 — осмысление и работа с инструментами


| Вопрос                                                                                                                       | Твой ответ                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
|------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)?                   | Обычные БД (OLTP) не справляются с аналитикой на петабайтах данных, а классические DWH дороги в масштабировании. Lakehouse позволяет хранить данные в дешевом объектном хранилище (S3/MinIO), но при этом работать с ними как с таблицами (ACID, SQL) благодаря табличным форматам (Iceberg). |
| Пример schema evolution на Silver: добавила/переименовала колонку - что произошло? | Выполнила `ALTER TABLE silver.lakehouse.orders_cleaned ADD COLUMN comment VARCHAR;`. Колонка добавилась мгновенно. Iceberg хранит схему в метаданных, а не в Parquet-файлах, поэтому старые данные не перезаписывались. В новых строках `comment` будет `NULL`.                                                                                                   |
| Пример скрипта восстановления данных из снапшота (time travel)                          | `SELECT * FROM silver.lakehouse.orders_cleaned FOR VERSION AS OF <snapshot_id>;` (или, например `FOR TIMESTAMP AS OF '2026-10-17 12:00:00'`). Это позволяет откатить данные, если в Silver случайно залила ошибочные.                                                                                                                                                                                                     |


### Подключение инструмента к lakehouse


| Инструмент    | Почему выбрала именно его                                                                                                                                                                                                                                                                                                                                                                                                       |
|-------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| DBeaver + MinIO Console | Вместо тяжелого BI-инструмента использовала DBeaver как SQL-клиент для выполнения запросов к Trino и MinIO Console для визуального контроля файлов. Это позволило продемонстрировать работу всех слоев Lakehouse без развертывания дополнительных контейнеров. |


**Скрипты развертывания:**

```powershell
# MinIO  
docker run -d --name lakehouse-minio -p 9000:9000 -p 9001:9001 -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin -v minio-data:/data quay.io/minio/minio:latest server /data --console-address ":9001"  

# PostgreSQL  
docker run -d --name lakehouse-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 -v pg-data:/var/lib/postgresql/data postgres:17  

# Миграции Lakekeeper  
docker run --rm -e "LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!" -e "LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres" -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres" quay.io/lakekeeper/catalog:latest-main migrate  

# Lakekeeper  
docker run -d --name lakekeeper -e "LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!" -e "LAKEKEEPER__PG_DATABASE_URL_READ=postgresql://postgres:postgres@host.docker.internal:5432/postgres" -e "LAKEKEEPER__PG_DATABASE_URL_WRITE=postgresql://postgres:postgres@host.docker.internal:5432/postgres" -p 8181:8181 quay.io/lakekeeper/catalog:latest-main serve  

# Trino  
docker run -d --name trino -p 8080:8080 -v "${PWD}\catalog:/etc/trino/catalog" trinodb/trino:476
```

 Мои действия:  
1. Подключилась к Trino через DBeaver (Host: \`localhost\`, Port: \`8080\`, User: \`trino\`).  
2. Выполнила \`SHOW CATALOGS\` - увидела каталоги \`bronze\`, \`silver\`, \`gold\`.  
3. Выполнила \`SHOW TABLES FROM bronze.lakehouse\` - увидела таблицы \`customer\` и \`orders\` (слой Bronze).  
4. Выполнила \`SELECT \* FROM bronze.lakehouse.customer LIMIT 10\` - увидела сырые данные.  
5. Зашла в MinIO Console (\`http://localhost:9001\`) - Buckets - \`bronze\` - увидела папки \`customer\` и \`orders\` с файлами \`.parquet\`, что подтверждает физическое хранение данных в объектном хранилище.  

## 7. Выводы

Работа показала, что медальон переносит стоимость вычислений из момента запроса в момент загрузки: на сыром Bronze Q18 джойнит 6 001 215 строк `lineitem` с `orders` и `customer`, а Gold отдаёт готовую витрину из 57 строк размером 0,002392 МБ — повторные запросы к витрине на порядки дешевле.

Эксперимент с кодеками на `lineitem` показал компромисс «размер ↔ скорость»: GZIP дал 148,27 МБ против 151,93 МБ у ZSTD (выигрыш 2,4 % по размеру), но разница во времени Q18 (6,078 / 5,269 с против 6,895 / 5,513 с) сопоставима с разбросом между первым и повторным запуском одного варианта (у ZSTD — 1,4 с). Отсюда методологический вывод: на sf1 надёжно сравнивать кодеки по размеру, а по времени — нет; для уверенного вывода по времени нужен sf3–sf5 или медиана из нескольких повторов. В пределах измеренного Parquet + ZSTD — разумный дефолт для Bronze и Silver, а для Gold кодек не важен из-за объёма в 57 строк.

Проверка Iceberg подтвердила, ради чего выбирают lakehouse: `ALTER TABLE ... ADD COLUMN` добавил столбец в `bench.silver.schema_test` без перезаписи 10 строк, а `FOR VERSION AS OF` вернул предыдущую версию (10 строк) после того, как в текущей уже было 11, — оба механизма работают на уровне метаданных, не данных. Apache Spark 3.5.5 через тот же каталог Lakekeeper прочитал `bench.bronze.lineitem` за 3,41 с и получил те же 6 001 215 строк, что и Trino: данные в открытом формате в объектном хранилище не привязаны к конкретному движку.

Ограничение работы — масштаб sf1 и один узел Trino на ноутбуке: на этом объёме разница между кодеками по времени чтения на границе шума, а MinIO работает локально, поэтому ввод-вывод дешевле, чем в настоящем облачном хранилище. В облаке выигрыш GZIP по размеру (2,4 %) мог бы стать заметнее по деньгам, но это предположение, а не измеренный факт.
